## 1. 実装済みの機能

- 7 種のミノ、10×20 の盤面、配置、1st〜7th の PC 番号を型で表すモデル。
- 3 値の条件評価（`satisfied`、`failed`、`pending`）。まだ見えていない NEXT を
  誤って「成立」と判定しない。
- `seen`、`not_seen`、順序、範囲付きの先頭部分、最後のミノの判定、到達可能性、
  HOLD/Current、論理演算の組み合わせ、構造化したキューのパターンの各条件。
- `[TJ]!,S` 形式の「順列＋先頭」を明示的なデータで表す。自由形式のパターン文字列を
  実行時に解釈することはしない。
- ルールとセットアップのセルに限り、J/L と S/Z の鏡像化を許す。解は鏡像化で
  作らない。
- 推薦の並べ順、局所的な優先度、失敗条件による除外、候補の診断レポート。
- 安定した観測だけを使うセッション追跡、NEXT 履歴の差分更新、1st〜7th の循環、
  確信度による足切り、手動の再同期、スナップショットへの巻き戻し（安定しなかった
  状態への Undo はキュー上の位置で見分ける）、Undo でセットアップの開始に戻った
  ときの解の切り替え。
- 出典情報付きの JSON ルール検証と、2 つの方針: 厳密に使うための検証済みだけの
  選択と、未確認の学習データを明示ラベル付きで出す参考プレビュー。
- 画像から起こした IJLO の転記（`data/ijlo/diagram_cells.json`）。左下原点・10 列の
  座標系、セル範囲の検証、テトロミノ形状の検証を持つ。元画像では先に消えた行も
  描かれたままなので、その行を `cleared_rows` に列挙し、詰めてから形を確かめる。
  その説明のない分断されたミノは警告として報告する。
- 後から確認したセットアップの形を実行時にルールへ結び付け、セットアップの進み具合を
  「正しい・足りない・食い違い・余計」の 4 種に分けて計算する（オーバーレイ描画用）。
- 利用者が行う 10×20 盤面のキャリブレーションと、安定フレームの関門。TETR.IO の
  表示倍率でセルの大きさが変わるため、盤面の中心・上端・幅をクライアント領域に
  対する比率で保存する。HOLD、Current、NEXT5 は固定の画面矩形ではなく、
  キャリブレーションした盤面からの相対位置で探す。認識結果は、確信度 70% 以上の
  同じ完全な観測が 3 フレーム続いたときだけセッション追跡に渡す。3 フレームの一致が
  アニメーションとノイズへの主な対策で、以前の 92% のしきい値は TETR.IO の
  アンチエイリアスされた通常のプレビューまで弾いていた。
- Windows 専用のウィンドウ探索。タイトルが `TETR.IO` で、TETR.IO Desktop のプロセス
  （`TETR.IO.exe`）が持つ可視ウィンドウだけを選び、クライアント矩形とプロセスを記録し、
  条件を満たす中で最大のものを使う。TETR.IO の内部は読まず、入力も監視しない。
  2026-10-22 まではタイトルだけで決めていたため、ゲームが最小化されているか小さいと、
  ページタイトルに「TETR.IO」を含むブラウザ（tetr.io 自体や GitHub 上のこのリポジトリ）を
  代わりに取り込んでいた。ブラウザ版 tetr.io には対応しない。
- Windows GDI によるクライアント領域の取り込み。上から下の順に並んだ RGBA フレームを
  検証して返す。`probe-capture --bmp <path>` はキャリブレーション用の任意の診断で、
  通常の取り込みではスクリーンショットを書き出さない。
- 10×20 盤面、HOLD、Current、NEXT5 の保守的なピクセル認識。明るい色と暗い色の
  TETR.IO の配色を、明示的なパレットと色相による予備判定で読み分ける。空や曖昧な
  プレビューは弾く。Current は盤面の出現領域でつながった 4 セルから求め、その操作中の
  ミノと、離れていてかなり暗いゴーストを固定ブロックから取り除く。確信度の低い状態は
  認識の段階で止める。Current が出現領域の外にあるフレームでは、落下中のミノを
  固定ブロックと見なさないよう状態の更新を止める（Current を探すのは出現領域の 3 行と
  上から 8 段目まで）。止めている間も、オーバーレイは最後に追跡した状態の案内を出し続け、
  状態行の末尾に `| last stable state: <理由>` を付ける（2026-10-23 から。以前は案内を消していた）。
- 最初の TETR.IO での実行（2026-10-18）で見つかった問題の修正。ドラッグ範囲が枠を
  含む（内側 192 px でなく 194 px）と最下段で 1/4 セルずれるため、キャリブレーションした
  盤面を見えている白に近い枠線に合わせる。TETR.IO はミノを盤面の 3 行上に出すので、
  Current はそこも探す。暗い HOLD は、1 行が 4 セル埋まり他の行が空のときだけ空の
  プレースホルダーと見なす。ゴーストの縁に出る色収差（1 セルあたり最大約 26 色画素）は、
  曖昧と判定するしきい値 40 を下回る。TETR.IO は固定ブロックを Current より暗く
  描くため、色付きのゴーストは Current を真下にずらしたものでなければならない。
  `tests/recognition_frames.rs` が録画フレームの切り抜きでこれらを確かめる。
- 診断用の `run-live`。ウィンドウ探索、取り込み、認識、3 フレームの安定判定、
  セッション追跡、ルール選択を通しで動かし、短い状態行を出す。`--reviewed-only` を
  付けない限り、オーバーレイと同じラベル付きプレビューの方針を使う。
- Windows の透明オーバーレイ（`run-overlay`）。見えている TETR.IO のクライアント矩形に
  追従し、最前面かつクリックを通す。認識の状態と、PC 2 で HOLD + Current + NEXT の
  先頭が IJLO のときに IJLO のセットアップのセルを描く。セットアップが完成し、
  プレイヤーが `S` か `Ctrl+Alt+S` を押すと、検証済みの解の残りのセルを描く
  （各 PC の開始時は OFF）。状態が分からないときに古い推薦を使い回すことはない。
  2026-10-22 から、セットアップと解のセルはミノの色の薄い半透明の塗りで、
  セルごとではなくミノごとに輪郭を描く。今のミノのセルは濃く塗り、警告は赤。
  ウィンドウはピクセル単位のアルファ（`UpdateLayeredWindow`）を使うので、落下中の
  ミノが塗りの下から見える。接する同じ種類のミノは輪郭を共有する。

## 2. IJLO の転記状況

`data/ijlo.json` は、`Algebruh's 2nd Methods.md` の 20〜32 行目にある 5 つの
セットアップ群と元画像を対応付けている。セットアップの条件は IJLO の 4 個に続く
バッグで評価する（`EvalContext::for_following_bag`）。ケースのミノとその後のバッグは
`[TJ]!,S` 形式の条件には数えない。

- `ijlo_s_queue`（画像 4）と `ijlo_z_queue`（画像 1）は `verified`。T を残し、
  T と J の両方が S より先に来たとき（T と L の両方が Z より先のとき）は、間に別の
  ミノがあっても失敗する。両方組めるときは、鍵のミノが先に来た方を選ぶ。
- O を残す 2 つ（左が画像 7+8+9、右が 10+11+12）は 2026-10-18 から `verified`。
  資料にキュー条件がないので導いた: HOLD なしでは、左の解は J が I より先、T が Z より先、
  T と J が L より先を要する（L は y=1 の行を通り、その行を完成させるのは画像 8 の T と J
  だけ）。右は J/L と S/Z を入れ替えたもの。`ordered_with_hold` が、バッグのまだ見えない
  全ての続きについて HOLD 1 枠でこの前提を評価する（残した O は来たときに HOLD に入る）。
  それぞれ 5040 通りの順序のうち 1344 通りを満たす。資料ではこれを S/Z キューの
  セットアップが両方失敗したときだけ使うので、そのときまで待つ。同点なら資料の順で左。
- サンドボックスの拡張（画像 13）は `review_required` のまま。きっかけが本文に
  はっきり書かれておらず、スキムと 180 度回転を分析していない。
- S/Z キューと O 残しの解は `verified` で、セルを `data/ijlo.json` に持つ。
  `tools/ijlo_solves.py verify` は続くバッグの全ての順序を HOLD 1 枠で、SRS の 90 度の
  動き（標準のキック、180 度回転なし）で打ち、各解がそのセットアップの条件の受け入れる
  順序でちょうど到達できることを、PC 開始時の HOLD が空でも埋まっていても確かめる。
  SRS の到達可能性は置いたミノの組ごとに 1 度だけ計算して保存するので、全体で約 2 秒。
  `tools/ijlo_solves.py fixtures` は `tests/fixtures/ijlo_reachable_orders.json` も書き出し、
  `tests/ijlo_conditions.rs` が Rust の条件がちょうどその順序を受け入れることを確かめる。
  サンドボックスの解は `review_required` のまま。
- `last_among` は 1 バッグの範囲で早めに決める。他のミノが全て見え、鍵のミノが
  見えていなければ、鍵のミノは最後になる。
- `evaluate_solve_progress` はセットアップと解を実際の盤面に重ねる。資料は行を
  消さずに PC 全体を描くので、どのフレーム行が消えたかを推定して残りのセルを報告し、
  決められないときは `Ambiguous` / `Inconsistent` を返す。ルール選択は、検証済みの解で
  盤面が説明できる限りセットアップを保つので、解のミノを早めに置いたり行が消えたり
  しても案内が消えない。`run-overlay` が解の残りのセルを描くのは、結果が
  `InProgress` でセットアップのミノが全て置かれているときだけで、`Ambiguous` /
  `Inconsistent` では何も描かない。

既定のオーバーレイは未確認のセットアップを `IJLO reference guidance ... (unreviewed)` と
して描く。`--reviewed-only` を付けると出さないので、厳密モードでは S/Z キューの
セットアップが両方失敗した時点で止まる。

## 3. 資料全体からのケース自動生成

`tools/build_cases.py` は、元資料の `###` の各節を手で転記せずに
`data/cases/<CASE>.json`（49 ケース、約 500 セットアップ）に変換する。

- 埋め込み画像をセルごとに読む（`tools/diagrams.py`）。灰色の文脈のない画像は
  セットアップで、そこにミノを足した後の画像は 2 段階で描いた同じセットアップ
  （キュー依存のセットアップ）。解の画像は、灰色の文脈によってセットアップ、その前の
  段階、または鏡像のセットアップに対応付ける。セットアップを灰色だけで描く節
  （TJOO の PCO+O）はケースのミノで敷き詰め、セットアップより外の灰色セルは
  3 個セットアップで余ったケースのミノとする。
- 資料はライン消去なしで PC を描くので、行が消えた後に置いたミノはその行をはさんで
  分かれて見える。色付きのセルを、そうした飛ばし行を許してテトロミノに分ける。
  分け方が複数あれば、SRS で置ける順序を持つ最初のものを使う。
- 解が `verified` になるのは、セットアップと解で行がちょうど埋まり、行が揃うたびに
  消しながら SRS の 90 度の動き（標準のキック）で置ける順序があるとき。生成した解は
  全て通る。セットアップのミノを先に置くが、セットアップ完成前に解のミノを
  セットアップのミノの下へ差し込まないと成り立たない解（TTOZ の image823 で Z の下の L）は
  例外で、その配置表にはセットアップのミノも入る（`setup_in_table`）。
- 段階付きの図: 最後の段階の空きがミノ 2 個分以下なら（image55、180〜182、791）、
  まだ使えるミノで空きを敷き詰め、SRS の順序を持つ敷き詰めを全て解とし、
  「completed ... by search」と注記する。空きがもっと多い図は最初の数手か
  セットアップの一段階だけを示すもので（image96、148、154、435、680、681）、
  セットアップの注記に残し、解にはしない。
- 解のないセットアップは、同じセルとミノを持つセットアップ（TJLS の image361/362）か
  鏡像（JLSZ の image159/160）から解を借り、SRS で確かめ直す。JLOS の image94
  （JIO のキュー依存の段階）は資料に解がなく `review_required` のまま。
- セットアップの `build_condition` は `solvable`: 2nd PC の開始（その時の HOLD、
  キュー順のケースのミノ、続くバッグ）から HOLD 1 枠で打つ。セットアップのケースの
  ミノを好きな順で先に置き、続いて解の SRS 配置表に従うので、バッグ開始時にまだ
  HOLD が埋まっている状況も扱える。ケースの開始が分からないときは、残りのケースの
  ミノとバッグを空の HOLD から打つ。本文からキューのルールは取らず、本文は
  セットアップの注記に残す。キュー依存のセットアップが続くバッグから取るミノは、
  解の前に置く。
- `ABCD/ABCE` の節は両方のケースを書く。各セットアップはミノが合う方のケースに入り、
  もう一方へは鏡像にして入る。自分自身が鏡像のケース（JLSZ、TISZ など）は両方の向きを
  持つ。キック表が対称ではないため、鏡像は SRS で探し直す。
- 選択: バッグの全ての続きで `solvable` が成り立てば、通常どおりそのセットアップを選ぶ。
  どれも決まらないうちは、盤面に合う限り、残りのバッグ順序を最も多く解ける検証済みの
  セットアップを出す（理由は `likely: ...`）。
- `run-overlay` は `data/ijlo.json`（手で確かめた IJLO）と `--cases`（既定は
  `data/cases`）の全ファイルを読み、手作業のデータが既に扱うミノのケースは生成分を
  使わない。ケースは 2nd PC 開始時の HOLD と先頭のミノを並べ替えたものなので、
  TJJO のような重複のあるケースも認識する。

```powershell
python -I tools/build_cases.py report           # 節ごとの解析の要約
python -I tools/build_cases.py report TJOO      # 1 ケースの詳細
python -I tools/build_cases.py write            # data/cases/*.json（約 6 分）
python -I tools/build_cases.py coverage         # セットアップごとのバッグの割合と
                                                # tests/fixtures/cases_coverage.json
cargo test --test generated_cases               # 5040 通り全てで Rust の solvable と Python が一致
```

`tests/fixtures/cases_coverage.json` は、検証済みの各セットアップを、バッグだけの場合と
3 通りのケース開始（HOLD が空、最初のケースのミノを保持、最後のものを保持）で
確かめる。まだ扱っていないもの: 180 度回転（資料は一部の解に「needs 180」と記す）と、
本文が網羅率ではなく組みやすさで選んでいるセットアップ。

## 4. 検証

GitHub Actions（`.github/workflows/ci.yml`）が、プルリクエストと `main` への push の
たびに、きれいな Windows のチェックアウトで `cargo fmt --check`、
`cargo clippy --all-targets -- -D warnings`、`cargo test --release`（生成ケースの
テストは最適化なしだと数分かかる）を走らせる。ワークフローはローカルの
ツールチェーンと同じ Rust 1.97.1 に固定している。新しい版は Clippy の検査を増やす
（Rust 1.99 は `chunks_exact(4)` と手書きの最下位ビット取り出しを指摘する）ので、
固定はローカルのツールチェーンと一緒に上げる。CI が見るのはリポジトリ自体の中身だけで、
Python のツール、記録した TETR.IO のセッション、TETR.IO の起動が要るものは手元で確かめる。

```powershell
cargo test
cargo run --bin validate-rules -- data/ijlo.json
cargo run --bin validate-diagrams -- data/ijlo/diagram_cells.json
python -I tools/ijlo_solves.py verify
cargo run --bin probe-window
cargo run --bin probe-capture
cargo run --bin configure-overlay
cargo run --bin probe-recognition -- --bmp <captured.bmp>
cargo run --bin run-live -- --once --verbose
cargo run --bin run-overlay
```

`Cargo.toml` の `default-run` が `run-overlay` なので、`cargo run` だけでもオーバーレイが
起動する。

`run-live --record-dir DIR [--record-max N]` は各フレームの詳しい要約を `DIR/log.txt` に
書き、確かな観測にならなかったフレームを最大 N 枚（既定 40）、0.7 秒に 1 枚まで BMP で
保存する。`probe-recognition --bmp PATH --cells` はセルごとのミノと分類した画素数を、
上の行から出す。

`run-live` は `--once` を付けなければ 100 ms ごとに取り込み続ける。`--once` は
キャリブレーションと簡単な確認に、`--verbose` は領域ごとの確信度と求めた盤面矩形の
表示に使う。既定のキャリブレーションは観測した 1920×1009 の TETR.IO Desktop の
クライアント領域に合わせてあるので、表示倍率が違うときは認識を信じる前に設定する。

## 5. PC 番号と解の表示

PC 番号は 1 から始まり、空でない盤面から空の盤面への安定した遷移で進む。

TETR.IO の Undo（`Ctrl+Z`）で前の状態に戻ると、PC 番号とその PC の開始（`current_pc_start`）
も戻る。追跡側は、ゲーム開始（または再同期）からの NEXT を PC で区切らずに 1 本の
キューとして持ち、各スナップショットに「NEXT5 がキューのどこで終わるか」
（`Snapshot::queue_end`）を記録する。観測は次の順で判定する。

1. 過去のスナップショットと完全に一致する: そこへ巻き戻す（従来どおり）。
2. 一致しないが、NEXT5 の 5 個がキューの過去の並びと一致する: 安定しなかった状態への
   Undo とみなす。その位置以前で最新のスナップショットまで巻き戻し、そこから観測へ
   進める。巻き戻し先が PC の前（盤面が空でない）で観測の盤面が空なら、その PC を
   数え直す。安定判定は同じ観測が 3 フレーム続くことを求めるので（既定の 100 ms 間隔で
   約 300 ms）、素早く置いた状態は履歴に残らず、以前はこの Undo が完全一致に
   ならなかった。そのとき NEXT が巻き戻っているため前進として受け付けられず
   （`history_discontinuity`）、同じ位置まで打ち直すと前の PC の続きを次の PC として
   受け付けて、次の PC 番号が 1 つ進みすぎた。PC 直後の空の盤面への Undo では、
   「空でない盤面から空の盤面」として PC をもう 1 回数えていた。
3. HOLD が空になった、または最初の HOLD の前に NEXT が続かない: 新しいゲーム。
4. それ以外: 通常の配置、ライン消去、PC として進める。

前進で NEXT の 3 個以上が前の NEXT5 から続くとき（1〜2 個置いたとき）は、2 を試さず
前進とする。7-bag では 5 個の並びが繰り返すことがあり、前進を Undo と取り違えない
ため。HOLD が空の観測は、巻き戻し先に HOLD があれば Undo とみなさない（HOLD は同じ
ゲーム中は空にならないため、リセット）。見分けられないもの: 一度も安定しなかった
PC をまたぐ Undo と、再同期・リセット・続かない PC より前への Undo。TETR.IO の Undo
が HOLD をどの時点の状態に戻すかは、TETR.IO では未確認。

`run-overlay` の実行中に `Ctrl+Alt+1`〜`Ctrl+Alt+7` を押すと、途中から起動したときや
認識を誤ったときに番号を合わせ直せる。オーバーレイの状態行は、PC 2 を待っているか、
4 個のケースが IJLO でないか、どの IJLO セットアップが有効かを示す。

ZEN の設定で統計を表示していると、盤面の左に PIECES（置いたミノの数）が出る。
`pieces_ocr` は盤面の左の文字を行に分け、`PIECES` という見出しを型紙で見つけ、その
すぐ下の行のカンマより前の大きな数字を読む。どの統計がどの順に出るかは設定で変わるので、
位置は決め打ちしない。PC ループでは 1 回の PC に 10 ミノ使うため、
`(PIECES ÷ 10) mod 7 + 1` がその時点の PC 番号になる。2 フレーム続けて同じ値が読め、
かつ安定した観測が確定したときだけ、`SessionTracker::align_pc_ordinal` で番号を合わせる
（今の PC の履歴は番号を付け替えて残すので、Undo は使える）。見出しが無い、数字が型紙に
十分近くない、などで読めないときは、従来の空盤面による数え方をそのまま使う。状態行には
番号の出どころ（`PIECES n` か `own count`）が出る。数字の型紙のうち 5 と 8 は、録画に
PIECES の値として現れなかったため、盤面下のスコアの字形から作っている。

TETR.IO は盤面の表示倍率に合わせて左の文字も拡大・縮小する。比べるのは文字の外接矩形に
かけたマス目（数字 6×9、見出し 24×5）の明るさで、明るさも最大値で割るので、距離は倍率に
よらない。ただし小さい文字ほどにじむため、型紙は録画を 0.45〜2.3 倍に縮尺し直した平均で作り、
しきい値も倍率ごとの距離の分布から決めた。数字は「型紙との距離 4 以下」かつ
「2 番目に近い数字が 1.4 倍以上遠い」、見出しは距離 8 以下で受け入れる。縮尺し直した録画では、
0.7 倍（盤面の幅およそ 135 px）以上で全て正しく読め、それより小さいと読めない扱いになる
（誤った値は出なかった）。実際の描画は縮尺し直しよりくっきりしているはずだが、実機での
確認はまだない。PIECES が読める
間は `Ctrl+Alt+1..7` で合わせても次の確定で PIECES の値に戻る。

解の表示（追跡側の案内状態の `show_solve`）は各 PC で OFF から始まるので、セットアップを
完成させただけで解が見えることはない。検証済みの S/Z キューのセットアップが完成すると、
状態行が `IJLO setup complete (...); press S to show the solve` になり、何も描かない
（プレイヤー自身の解を「ずれ」として示さないため）。その後は次のとおり。

- `S` で表示を ON にする。OFF にはしない。`S` はゲームのキーでもあり得るため
  （オーバーレイはキーの状態を読むだけなので、TETR.IO にもキーが届く）。
- `Ctrl+Alt+S` で ON と OFF を切り替える。
- セットアップの完成前に押すと表示は OFF のままで、状態行に約 1.5 秒
  `| solve hotkey ignored: setup not complete` と出る。受け付けたときは
  `| solve shown` か `| solve hidden` と出る。

ON のときは、完成したセットアップの代わりに検証済みの解のセルを描き、置いた解の
ミノは行が消えるにつれて表示から消える。PC の切り替わりと `Ctrl+Alt+1..7` の再同期で
OFF に戻り、Undo で前の状態に戻るとその状態の設定に戻る。詳細行の末尾は `solve ON` か
`solve OFF`。

## 6. 統合案内（資料のルール + Setup Konbini）

2026-10-21 から、`run-overlay` はモードを切り替えずに 1 つの案内を出す（以前の
`Ctrl+Alt+K` による Setup Konbini モードはこれに統合した）。

- 2nd PC: 上記の資料のルール（`data/ijlo.json`、`data/cases/*.json`）を優先する。
  そのケースのデータがないか、盤面とキューに合うセットアップを選べないときは、
  今のキューで組める 2nd PC の Setup Konbini のセットアップを代わりに出し、詳細行に
  理由を書く（`guide=Konbini (source: ...)`）。
- それ以外の PC: その PC 番号の Setup Konbini のセットアップ。
- 状態行は出どころを示す: `PC Overlay [source]: ...` か `PC Overlay [Konbini 2nd]: ...`。
  詳細行の末尾は `guide=source` / `guide=Konbini`。
- 2026-10-22 から、資料のセットアップは引用している行から `Algebruh's 2nd Methods.md` の
  節の名前も示す:
  `TILS guidance active (tils_image434_m · Odd JL, with T › TIJZ/TILS (mirrored))`。
  `(mirrored)` は節のケースの鏡像として生成したケースの印。資料はリポジトリの
  ルート（ルールの `data/` の親）から読み、見つからなければ節の名前は省く。

ホットキー（2 モード版からの変更は太字）:

| キー | 動作 |
|---|---|
| `S` / `Ctrl+Alt+S` | セットアップ完成後に解を表示 / 切り替え（従来どおり） |
| `Ctrl+Alt+1..7` | PC 番号を合わせ直す（従来どおり） |
| `Ctrl+Alt+N` / `Ctrl+Alt+B` | Setup Konbini の次 / 前の候補。**常に有効になり、新しい PC の開始時に最善の候補へ戻る** |
| **`Ctrl+Alt+K`** | **以前: Setup Konbini モードの ON/OFF。現在: 資料のルールがあっても 2nd PC で Setup Konbini を使う（もう一度押すと戻る）** |
| `Ctrl+Alt+F` | シートを取り直す（従来どおり） |

ホットキーは、専用スレッドに置いた低レベルのキーボードフック（`WH_KEYBOARD_LL`）で受け取る
（2026-10-23 から）。以前は認識の 1 周ごとに `GetAsyncKeyState` でキーの状態を見ていたため、
1 周（認識と 100 ms の待ち）より短いタップを見逃し、押下の 3 回に 1 回ほどを取りこぼしていた。
フックは押下を 1 回ずつキューに積み、ループが次の周でまとめて処理する。押しっぱなしの
自動リピートは 1 回と数える。キーは横取りせずに次へ渡すので、`S` などはゲームにも届く。
フックはシステム全体のキーを見るため、押下は TETR.IO が手前（フォーカスあり）のときだけ数える。

TETR.IO が手前にないとき（`GetForegroundWindow` が TETR.IO のウィンドウでないとき）は、
オーバーレイを隠し、取り込みと認識も止める。安定待ちの途中の候補は捨てるが、追跡した状態は
そのまま残るので、TETR.IO に戻ると続きから案内する。オーバーレイ自身はクリックを素通しし
フォーカスを取らない（`WS_EX_TRANSPARENT` と `WS_EX_NOACTIVATE`）ので、この判定を乱さない。

シートは起動時に `data/konbini/` から読み、**そのフォルダが空なら起動時に裏で
ダウンロードする**（以前は最初の `Ctrl+Alt+K` のとき）。その間、状態行に
`fetching Setup Konbini...` と出る。完成した Konbini のセットアップには PC 解の探索
（[7 章](#7-pc-解の探索srs)）で解を付ける。

テスト: `cargo test --bin run-overlay` が、2nd PC での資料優先、`Ctrl+Alt+K` による
上書き、理由を注記に書いた代替、他の PC、完成した資料のセットアップで `S` が効くこと、
データがないときのメッセージを確かめる。TETR.IO ではまだ試していない。

### Setup Konbini のデータと組み立ての探索

1st〜7th の全ての PC のセットアップは、公開されている
[Setup Konbini](https://docs.google.com/spreadsheets/d/1tI9fPeeEEEhWS2h0Gzib5UIjLKN33wd18WQSKRjxYMw/edit)
のスプレッドシートから取る。今の HOLD とキューで組めるセットアップだけを出す。

`cargo run --bin fetch-konbini` で同じファイルをコンソールから取れる。各
`Nth: Data` シートを、システムの `curl` で CSV として取得し（`gviz/tq?tqx=out:csv`。
スプレッドシートが公開されている間は使える。Windows では `System32\curl.exe` を絶対パスで
呼び、HTTPS のみ・1 シート 32MiB までに制限する）、`data/konbini/1st.csv` 〜 `7th.csv` に
保存する。このフォルダはコミットしない。シートでは、`FUMEN` の見出しごとに 1 つの
ブロックが始まり、その左で最も近い `ID` と `SOL` の列がそのブロックのもの。5th PC の
シートには `SOL` の見出しがなく、glue の fumen の後の割合の列を使う。セットアップの
セルは fumen の 1 ページ目から取り（`src/fumen.rs`）、灰色のセルは「どのミノでもよい」と
して描く。2026-10-21 時点のシートは 1st〜7th PC で 184 / 359 / 363 / 266 / 802 / 476 / 75 個の
セットアップを持ち、全てが完全なテトロミノに分解できる（`tests/konbini_data.rs`、
キャッシュがなければ飛ばす）。

追跡している PC 番号のシートを使う。セットアップが候補になるのは、次の全てを
満たすとき。

- その PC がミノを供給できる（素早い絞り込み）: `k` 個のセットアップは、PC 開始からの
  最初の `k + 1` 個（HOLD が先頭、HOLD 1 枠）から組めなければならない。
- 盤面が組み途中のそのセットアップである: 全てのブロックが同じ色のセットアップの
  セルである。セットアップが埋める行はゲームでは消えるがシートの図には残る
  （179 個のセットアップがそうなる）ので、消えた行を推定し、残りのセルを実際の盤面の
  位置に描く。
- 今の HOLD、Current、NEXT からまだ組める（`src/finder.rs`）。

組み立ての探索は knewjade の solution-finder にならう: ビットボードの盤面、位置と回転の
幅優先探索でミノを固定できる全ての配置を見つける手生成（横移動、ソフトドロップ、
TETR.IO の SRS+ キックによる 90 度と 180 度の回転。盤面とミノごとにキャッシュ）、
そして HOLD 1 枠でミノの順序を深さ優先で探し、失敗した状態を覚える探索。2 つの
枝刈りがある: HOLD と残りのキューに、まだ置いていない色付きのテトロミノそれぞれの
ミノが残っていること。ライン消去のないセットアップでは、まだ埋まっていないセルが
4 の倍数のセル数のかたまりに分かれること。SRS+ の表は、TETR.IO エンジンの再実装
triangle.js が再現した TETR.IO のもの（`src/engine/utils/kicks/data.ts`、y は下向き、
キックなしの回転の後に試す）。solution-finder には SRS+ の表がない。

7 個のセットアップには NEXT の後のミノが 1〜2 個要る。その選択肢は、PC を回し続ける
前提（1 PC あたり 10 個）で 7 バッグから求める。全ての選択肢で組めるセットアップを
先に、一部で組めるものを `depends on next pieces` を付けて後に出す。solution-finder の
割合と同じく、各選択肢はキュー全体が分かっているとして判定する。候補はその後
シートの `SOL` の割合で並べ、セットアップの案内と同じように描く（Current のミノは
塗りつぶす）。表示中のセットアップの `SOL` は、盤面の左上のすぐ上に `PC 100.00%` の形で
大きく描き、完成後に探した PC 解を表示している間も残す。安定していないフレームでは何も描かない。状態は 1 度だけ探索し、盤面・
HOLD・キューが変わるまで結果を使い回す。

確認（`tests/konbini_data.rs`、キャッシュあり）: 色付きで描かれた 2424 個の
セットアップは全て、自分のミノのある順序で組める。全順序で見ると平均 88.4% の順序で
組め、1489 個はどの順序でも組める。各 PC の開始から、ランダムな 7 バッグのキューと
空のキャッシュで、探索は平均 0.1〜8 ms、最悪 26 ms（5th PC）
（`cargo run --release --example konbini_timing` で計測）。2026-10-21 に TETR.IO で試し、
問題は報告されていない。セットアップの後の解とシートのカバー率のデータは使っていない。

## 7. PC 解の探索（SRS+）

利用者の判断（2026-10-21）で、knewjade の solution-finder を SRS+ で使うことにした。
Java の `sfinder.jar` を呼ぶのではなく、そのパーフェクトクリア探索を Rust で
再実装して `src/finder.rs` に組み込んでいる。

| | `finder.rs` の Rust（採用） | `sfinder.jar` を別プロセスで |
|---|---|---|
| 速さ | 実際の探索 1 回あたり平均 3.6 ms、最大 31 ms（後述） | JVM の起動だけで 1 回数百 ms。常駐させるには通信の取り決めが要る |
| 配布 | 追加なし。オーバーレイは `.exe` 1 つのまま | Java の実行環境と、オーバーレイの隣に jar が要る |
| SRS+ | 組み立ての探索で使っている TETR.IO の表（triangle.js）と同じ。180 度回転も含む | sfinder に SRS+ の表はない。キックのファイルがこの表の複製になり、ずれるおそれがある |

探索は solution-finder のパーフェクトクリア用の 2 層にならう。

1. 4 ライン（以下）の盤面の空きを、使えるミノで順序を無視して敷き詰める。各手は
   最も下の空きセルを覆う。行が消えた後に置いたミノはその行をはさんで分かれて
   描かれるので、高さ `k` 行の形は描画上の行のうち任意の `k` 行を取れる
   （solution-finder のライン消去を考える配置）。
2. その敷き詰めを打てる順序があれば残す: 各ミノは HOLD 1 枠でキューから来て
   （キューが尽きた後に HOLD を使ってもよい）、その時点の盤面で SRS+ の動きで着地し
   （上の手生成。盤面とミノごとにキャッシュ）、分かれて描かれる原因の行が消えてから
   置く。

`Finder::perfect_clears` は、一番上のブロックの高さから 4 行まで、空きをミノで埋められる
最も低い高さを試す。`konbini::find_perfect_clears` はこれを実際の盤面に対して、画面に
出ている HOLD、Current、NEXT5 だけで走らせる。シートの `SOL` は次のバッグの 7 個全て
（1 個は HOLD に残ってよい）の全順序を数えるが、2nd PC のセットアップの後の Current と
NEXT はそのうち 6 個しか見せない。`cargo run --release --example konbini_sol_rate` で
2nd PC の 100% のセットアップを 5040 通り全てで測ると、6 個では 41〜57%、7 個目を入れると
100.00% で、SRS+ の探索はシートと一致する。2026-10-22〜23 の版は、7 バッグで決まる
7 個目（各 PC を 10 個と仮定したバッグの位置から推定）も探索に入れていたが、位置の推定が
ずれると見えていないミノを使う解を出し、推定が正しくても 7 個目が見えるまでは HOLD と NEXT
で組めない解になっていた。今は見えているミノだけで探し、1 個置いて 7 個目が NEXT に
出たら探し直す。表示中の解は、観測が変わるたびに今の HOLD と NEXT でまだ最後まで打てるか
確かめ直し（`FoundSolve::playable`）、打てなくなった解は外す。ミノの順序を直接
探す最初の版（全配置の深さ優先探索）は、約 10 万の盤面で手生成が要り、7 個の探索 1 回に
約 1 秒かかった。先に敷き詰めることで数ミリ秒に縮んだ。

`run-overlay` では、表示中の Setup Konbini のセットアップが完成したとき（または盤面が
どのセットアップにも合わないとき。たとえばプレイヤーが独自の形にした）、その状態で
1 度だけ解を探し（最大 100 個）、次のようにする。

- 状態行は `N perfect clear(s) found (4 lines); press S to show the solve`。
- `S` / `Ctrl+Alt+S` で従来どおり表示 / 切り替え。解の残りのセルをセットアップの
  セルと同じように描く（Current のミノは強調）。
- 解がある間、`Ctrl+Alt+N` / `Ctrl+Alt+B` は解を切り替える（なければセットアップを
  切り替える）。状態行は `perfect clear i/N (search, SRS+, 4 lines)`。
- その後の盤面は、セットアップと同じく解を図として読み（消えた行を推定）、置いた
  ミノは表示から消える。見つけたどの解にも従わない盤面になると、解を捨ててその
  盤面から探し直す。

資料のルールがある 2nd PC は資料の解（`[source]`）を使い、探索した解は Setup Konbini の
案内に使う。

確認:

- `tests/pc_solutions.rs`: 資料の検証済みの解 1008 個（`data/ijlo.json` と
  `data/cases/*.json`）は全て、完成したセットアップから、解のミノを任意の順にして
  探索で見つかる（各ミノをその種類のセルに限る。これで除かれるのは他の解だけ）。
  資料の解は SRS の 90 度の動きで確かめたもので、全て SRS+ でも到達できる。
- `cargo run --release --example pc_timing`: 同じ 1008 個のセットアップで、解のミノを
  混ぜてキューにし、HOLD は空、キャッシュも空。7 個以下の探索 988 回（オーバーレイが
  見る範囲）は平均 3.6 ms、最悪 31 ms。9 個まで（1 個のセットアップ）では平均 7.7 ms、
  最悪 475 ms。1008 個のキューのうち 950 個で PC ができ、比べられる 921 件のうち 567 件で
  資料の解そのものが含まれる（混ぜた順序だと資料の解が使えないことが多い）。
- `cargo test --bin run-overlay`: 組んだ TILJ のセットアップが告知され、`S` で 24 セルの
  解が出て、`Ctrl+Alt+N` で別の解に切り替わり、置いた解のミノが表示から消える。

未実装: 資料のセットアップで資料の解が使えないときの解、NEXT の後のまだ見えない
ミノ、TETR.IO での確認。

## 8. 設定ウィンドウ（`pc-overlay-gui`）

```powershell
cargo build --release
.\target\release\pc-overlay-gui.exe      # リポジトリのフォルダから実行する
```

4 つのボタンと状態の文章を持つ小さなウィンドウで、1 秒ごとに更新する。

- **Start overlay / Stop overlay**: ウィンドウと同じフォルダの `run-overlay.exe` を
  起動する（停止はプロセスを終了させる。オーバーレイには Ctrl+C の他に終わる手段がない）。
- **Calibrate board**: `configure-overlay.exe` を起動する（盤面をドラッグし、Enter で
  保存、Esc で取り消し）。その後オーバーレイを起動し直す。
- **Download Setup Konbini**: `fetch-konbini` と同じダウンロードを裏で行う。
- 状態: オーバーレイとキャリブレーションが動いているか、保存したキャリブレーションの
  比率（または既定の設定を使っていること）、見つかった資料のルール、7 つの Konbini の
  シートのうちキャッシュ済みの数、最後のメッセージ。その下にホットキーの一覧。

選んだ方式: オーバーレイが既に使っている `windows-sys` による素の Win32（`BUTTON` と
`STATIC` のコントロール、1 秒の `WM_TIMER`）で、GUI のために依存を増やさない。
egui/eframe は 4 つのボタンと文章のために GPU か GL のバックエンドと約 200 個の crate を
足すことになる。編集できる設定や盤面のライブプレビューを持つようになったら検討する。

テスト: `cargo test --bin pc-overlay-gui`（状態の文章、データがないとき、ホットキー一覧）。
2026-10-21 にウィンドウを開いて取り込み、配置を確かめた。ボタンは押していないので、
そこからのオーバーレイとキャリブレーションの起動、ダウンロードは確認していない。

今後の設計メモ: ウィンドウはオーバーレイのプロセスが動いているかしか知らない。
オーバーレイ自体の状態（PC 番号、案内の出どころ、解の数）を出すには `run-overlay` からの
経路が要る。たとえば標準出力に状態行を書いてパイプで読むか、小さな JSON ファイル。
編集できる設定（パス、`--reviewed-only`、Konbini を優先するか）は、起動する
オーバーレイのコマンドライン引数にする。

## 9. TETR.IO の表示倍率のキャリブレーション

TETR.IO のウィンドウに通常の ZEN の盤面が見えている状態で、次を実行する。

```powershell
cargo run --release --bin configure-overlay
```

TETR.IO の上に一時的な暗い選択面が出る。盤面の左上の角から右下の角までドラッグし、
Enter で保存する。Esc なら既存のキャリブレーションを変えずに取り消す。選択した矩形は
クライアント領域に対する相対位置で、タイトルバーは取り込む画像に含まれない。
HOLD/NEXT は保存した盤面のセルの大きさから求めるので、別に選ばない。

スクリプトや画面なしでキャリブレーションするときは、マウスの代わりに値を直接渡せる。
`--cell-px` は取り込んだクライアント画像での盤面 1 セルの大きさで、盤面全体の幅は
その 10 倍。盤面全体を測る方が楽なら `--board-width-px N` を使う。`--top-px` は盤面の
上端、`--center-x-px N` は既定の横方向の中心を上書きする。

```powershell
cargo run --release --bin configure-overlay -- `
  --board-width-px 94 --top-px 406 --center-x-px 474
```

TETR.IO の表示倍率やクライアントの配置が変わったら、キャリブレーションをやり直す。
コマンドは `data/overlay-calibration.json` を書く。このファイルは画面ごとの設定なので
Git では追跡しない（`.gitignore` 済み）。ファイルがなければ既定の 1920x1009 用の値を
使う。書式は `data/overlay-calibration.example.json`（中身は既定値）を参照。

オーバーレイと `run-live` はこのファイルを自動で読む。`--calibration PATH` で別の
ファイルを選べる。`probe-recognition --bmp PATH` はオフラインの診断で、求めた盤面矩形と
Current/HOLD/NEXT それぞれの結果を、セッションの状態を変えずに出す。

## 10. TETR.IO エンジンとシード

`src/engine.rs` は TETR.IO v19 のソロ用エンジンで、czsmall_nnue の
`trainer/ttrm_exact_replay.py` にある `ReplayMachine` のソロ部分を移植したもの。
TETR.IO の画面を読む代わりにゲーム自体を動かすアプリへの最初の一歩である。
MINSTD による 7 バッグの乱数列、180 度キック付きの SRS+、DAS/ARR/DCD/SDF の扱い
（DAS キャンセルと safelock を含む）、重力とその加速、移動・回転でリセットされる
固定猶予、Hold、クラッチ出現、`all-mini+` の回転入れ判定を扱う。ミノの Y 座標の
末尾の桁で落下判定が変わるため、浮動小数点の計算は `round(..., 6)` や Python の
浮動小数点の剰余を含め、Python の式の順序に合わせている。対戦のおじゃまブロック
（パケット、相殺、穴の乱数）は移植しておらず、代わりに `Engine::schedule_garbage` が
配置の後に指定の行をせり上げる。

`src/ttrm.rs` は `.ttrm` / `.ttr` のイベント列をエンジンで再生し、リプレイの `end` の
スナップショット（盤面、おじゃまのセル、HOLD、置いたミノの数、ライン数）と比べる。
ソロの `.ttr` には `full` のスナップショットも最終盤面もないので、`replay.options` から
空の盤面で始め、`replay.results.stats`（置いたミノの数、ライン数、HOLD の回数、
T-spin を含む消し方ごとの回数）と照らし合わせる。エンジンが実装していない設定
（別のキック表やバッグの種類、別の回転入れのルール、違う盤面の大きさ、
`allow180 = false`）は近似せずに拒否する。`no_szo` は、シードの最初のミノが S、Z、O で
ないときだけ受け入れる。クライアントがそのバッグをどう並べ替えるか確かめていないため。

```powershell
# 最終スナップショットだけ（おじゃまを受けた列は一致しない）。
cargo run --release --bin verify-ttrm -- <file-or-dir>...
# Python の再構成との配置ごとの比較。
python -I tools/ttrm_python_dump.py --reconstructor <czsmall_nnue>/trainer <file-or-dir> -o dump.json
cargo run --release --bin verify-ttrm -- --reference dump.json <file-or-dir>
```

2026-10-21 に、手元の TETRA LEAGUE の `.ttrm` 30 個（プレイヤーの列 564 本）が全て
最終スナップショットと一致し、68,686 回の配置の全てが Python の再構成と完全に一致した
（ミノ、回転、X、ビット単位の Y、時刻、HOLD、ライン数、盤面）。比較対象なしでは、
おじゃまを受けなかった 16 本だけが最終スナップショットまで一致する。再生は約 1.3 秒で、
Python の再構成は約 50 秒。同じ日に録った 40 ライン sprint の `.ttr`（102 個、HOLD 36 回、
4 ライン消し 7 回、T-spin ダブル 1 回、180 度で置いたミノ 14 個、`cancel` と `safelock` が
ON）も、最終の統計と Python の再構成の全 102 回の配置に一致した。
`tools/ttrm_python_dump.py` はそうした `.ttr` に同じように合成した `full` の
スナップショットを付ける。

`tests/engine_differential.rs` は、`tests/fixtures/engine_differential.json` の合成した
ソロの列（20 本。20G、有限の SDF、DAS キャンセル、重力なしを含む 5 通りの操作・重力の
設定）で同じ比較を行う。実際の `.ttrm` は他のプレイヤーのデータを含むのでコミット
しない。テスト用データは
`python -I tools/make_engine_fixture.py --reconstructor <czsmall_nnue>/trainer` で作り直す。

まだ扱っていないもの:

- 0 から 2 への 180 度キックの後ろの 2 項目（2 番目と 3 番目）を入れ替えても、
  リプレイ集も合成した列も検出しない。表は 2026-10-21 に実装と照らして確認し了承
  したが、この 2 項目はリプレイのデータでは確かめられていない。
- 再生したソロの `.ttr` は 1 つ（40 ライン）だけ。
- 対応するのは `all-mini+` の回転入れ、7 バッグ、10×40 の盤面だけ。
- 実時間のループ、入力、描画はまだない。

シード: リプレイのシードは `options.seed` にある。`recover-seed --replay <file>` は
各列のシードと最初の 3 バッグを出す。実際のプレイ中はシードが見えないが、MINSTD の
状態は 2^31 − 2 通りしかないので、`recover-seed <pieces>`（出現順。Current、NEXT の順で
Hold は含めない。例 `OSITJLZ OIJLTZS OSJTZIL`）は全 CPU コアで約 1.3 秒で全てを調べ、
続くミノを予告する。リプレイ集のあるゲームでは、7 個で 426,082 通り（約 2^31 / 7!）、
14 個で 94 通り、21 個（3 バッグ）で本当のシードだけが残る。TETR.IO のカスタムルームでは
シードを固定することもでき、その場合はゲーム開始前にキュー全体が分かる。
